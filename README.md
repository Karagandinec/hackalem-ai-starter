# HackAlem AI — каркас под трек «Добывающая промышленность»

Заготовка под хакатон **HackAlem AI** (Астана, МВЦ «EXPO»). Предметка выбрана заранее:
парк техники на разрезе и события с ней — отказы, простои, ТО, аварии. Конкретный кейс
внутри трека объявляют на площадке, поэтому модели широкие и рассчитаны на правку.

Здесь уже сделано то, что на любом хакатоне пишется первым и съедает первый час: запуск,
база, авторизация, дашборд, импорт данных, чат с агентом, логирование вызовов модели
и реалистичные демо-данные. Ставится за несколько минут.

**Даты** (с [hackalem.ai](https://hackalem.ai/)): 23.09 — офлайн-этап, старт 14:00;
24–28.09 — жюри и технические эксперты проверяют присланные проекты; 29.09 — Demo Day;
01.10 — награждение на Digital Bridge. Код смотрят не только на сцене, поэтому репозиторий
должен запускаться у постороннего человека с первого раза — это ровно то, что проверяет
`make check`.

**Демо в интернете:** `<ссылка появится после деплоя>` — п. 8.7–8.9 Положения требует, чтобы
проект был доступен по рабочей ссылке всё время проверки 24–28.09. Как поднять за 5 минут —
раздел [Деплой](#деплой-один-контейнер--одна-ссылка).

## Что уже готово

**Backend (FastAPI + SQLAlchemy + SQLite)**

- health-check, CORS, конфиг из `.env`
- три модели под предметку: `Asset` (техника), `Event` (событие с ней), `User` (сотрудник)
- CRUD, фильтры по статусу, типу, участку и датам
- дашборд диспетчера: готовность парка, простои, отказы, выработка + график по дням
- демо-авторизация без JWT (логин, токен, `Authorization: Bearer`)
- **импорт CSV**: BOM от Excel, разделитель `;`, русские заголовки колонок — понимает сам
- **выгрузка CSV** по тем же фильтрам, что и таблица
- seed-скрипт и генератор демо-данных: 140 единиц техники, ~420 событий, износ влияет на отказы

**Модуль `backend/app/ai/`**

- обёртка над OpenAI: ретраи, таймауты, лимит токенов, кэш ответов
- Structured Outputs — ответ строго по JSON Schema
- function calling с тремя инструментами: чтение из БД, запись в БД, агрегат
- **агент в несколько раундов**: модель уточняет запрос по итогам ответа базы, а не бьёт вслепую
- **оценка риска отказа**: модель смотрит наработку и историю событий машины и пишет вывод
  обратно в базу (`ai_label`, `ai_score`)
- **заглушка-фолбэк**: нет ключа или упал API — приложение продолжает работать
- таблица `ai_calls`: промпт, ответ, токены, латентность, стоимость каждого вызова
- эндпоинт сводки `/api/ai/metrics`

**Frontend (Vite + React + TypeScript)**

- тёмная тема, сайдбар, роутинг
- диспетчерская: 4 карточки-метрики, график простоев, таблица техники
- парк техники: импорт CSV, оценка риска в один клик, выгрузка результата
- чат с агентом со стримингом ответа (SSE) и показом вызванных инструментов по раундам
- страница AI-метрик

## Быстрый старт

Нужны Python 3.11+ и Node 18+.

```bash
git clone https://github.com/Karagandinec/hackalem-ai-starter.git
cd hackalem-ai-starter
```

**1. Ключи**

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

Открой `.env` и вставь `OPENAI_API_KEY`. Без ключа проект тоже запустится — AI будет
отвечать заглушкой, всё остальное работает.

**2. Зависимости и данные**

```bash
make setup
make seed
```

Нет `make` (обычное дело на Windows) — рядом лежит шим с теми же командами:

```powershell
.\make.cmd setup
.\make.cmd seed
```

**3. Запуск**

```bash
make dev          # или .\make.cmd dev
```

- фронт — http://localhost:5173
- API и Swagger — http://localhost:8000/docs
- демо-логин — `demo@hackalem.kz` / `demo`

**4. Проверка перед коммитом**

```bash
make check        # pytest + tsc --noEmit, обе команды завершаются сами
```

## Деплой: один контейнер — одна ссылка

Жюри и технические эксперты проверяют проекты 24–28.09 **без нас**, и Положение (п. 8.7–8.9)
требует рабочую ссылку. Локального `make dev` для этого не хватает.

Собран один образ: Node собирает фронт, дальше FastAPI отдаёт и API, и статику. Второй
хостинг и CORS не нужны — всё живёт на одном адресе.

```bash
docker build -t hackalem .
docker run -p 8000:8000 -e OPENAI_API_KEY=sk-... hackalem
# http://localhost:8000       — приложение
# http://localhost:8000/docs  — Swagger
```

**Render, бесплатно, ~5 минут:**

1. [dashboard.render.com](https://dashboard.render.com/) → **New** → **Blueprint**.
2. Указать этот репозиторий — Render сам прочитает `render.yaml` и соберёт `Dockerfile`.
3. В переменных сервиса вставить `OPENAI_API_KEY` (без него демо работает на заглушке).
4. Через несколько минут будет адрес вида `https://hackalem-terricon.onrender.com`.

Тот же `Dockerfile` без изменений разворачивается на Railway, Fly.io и любой VPS —
Render выбран только потому, что у него бесплатный план и деплой по одному файлу.

**Что важно знать про бесплатный план:**

- Диск временный: при рестарте база обнуляется. Поэтому в контейнере включён
  `SEED_ON_START=true` — пустая база наливается демо-данными сама (140 единиц техники,
  ~420 событий), и проверяющий никогда не увидит пустой дашборд. Непустую базу автосид
  не трогает: введённое во время демо не затирается.
- Сервис засыпает после 15 минут простоя и просыпается за ~40 секунд. Перед окном проверки
  и перед показом жюри ссылку стоит открыть заранее, чтобы она отвечала мгновенно.
- Health-check висит на `/api/health` — Render дёргает его сам и перезапускает упавший сервис.

Проверено локально: фронт собирается (`npm run build`), FastAPI отдаёт `index.html`,
статику и SPA-маршруты (`/fleet` по F5 возвращает приложение, а не 404), промах по
`/api/*` остаётся честным 404 с JSON, автосид на пустой базе даёт рабочий дашборд.

## Как подогнать под кейс

Трек известен, конкретный кейс — нет. Порядок действий, когда его объявят:

1. **Проверить модели.** `Asset` — главный объект (техника), `Event` — что с ним произошло.
   Если кейс окажется не про парк, а, скажем, про логистику руды или геологию — переименуй
   `Asset` в `Truck` / `Borehole` прямо в `backend/app/models.py`, поправь `schemas.py`
   и прогони `make seed`. Миграций нет намеренно.
2. **Перегенерить данные.** Марки техники, участки, типы событий и причины — в
   `backend/scripts/generate_demo_data.py`. Потом `make seed`.
3. **Поправить дашборд.** Четыре карточки и график считаются в одном месте — функция
   `dashboard()` в `backend/app/routers/core.py`. Там же `BREAKDOWN_TYPES` и `READY_STATUSES`.
   Метрику, где рост — это плохо, помечай `lower_is_better=True`, иначе фронт покрасит
   падение простоев красным.
4. **Настроить агента.** Промпт — `SYSTEM_PROMPT` в `backend/app/ai/agent.py`, число раундов
   инструментов — `MAX_TOOL_ROUNDS` там же. Нужен свой инструмент — добавь в
   `backend/app/ai/tools.py` (описание + функция + `TOOL_HANDLERS`).
5. **Подстроить разметку.** Что модель проставляет в `ai_label` / `ai_score` — задаётся
   инструкцией в `POST /api/ai/enrich` и схемой `ENRICH_SCHEMA`. Колонки файла для импорта —
   словарь `IMPORT_ALIASES` в `backend/app/routers/core.py`.
6. **Схема ответа модели.** Нужен строгий JSON — добавь схему в `backend/app/ai/schemas.py`
   и вызови `complete(..., json_schema=...)`.

## Потенциал развития

Сейчас это диспетчерская одного разреза: техника, события с ней, простои, оценка риска
отказа моделью. Предметка взята не из интернета — она записана со слов практика, который
четыре года управлял тремя карьерами и ДСК на 900 тыс. т/год (`DOMAIN_BRIEF.md`). Оттуда же
понятно, куда прототип растёт дальше.

**1. Простой считать деньгами, а не часами.** На производстве простой учитывают сразу на
четырёх уровнях: узел → участок → переработанное сырьё → отгруженный продукт. Один
остановленный конвейер — это одновременно простой участка, недовыпуск тонн и недоотгрузка
клиенту. Следующий шаг после текущих карточек — считать по этой цепочке, чтобы на экране
были не «3 186 часов», а недовыпущенные тонны и невыполненный план отгрузки.

**2. Каскад, а не отдельная поломка.** Простои редко одиночные: встал конвейер за грохотом —
сырьё девать некуда — исправная дробилка на входе стоит следом. Граф зависимости узлов
превращает историю событий в предсказание: «этот отказ остановит ещё три узла и снимет
столько-то тонн из плана смены».

**3. От оценки риска к плану ЗИП.** Хронический дефицит запчастей — одна из главных причин
затяжных простоев ДСК. Оценка риска отказа по наработке и истории уже есть; поверх неё
считается минимальный складской запас: что заказывать сейчас, чтобы не встать через месяц.

**4. Расчёт числа машин под цикл рейса.** Классический простой без единой поломки: рейс
~30 минут, выгрузка ~10, возврат ~15–20, а самосвалов на плече два — и одновременно стоят
и вскрыша, и приёмный узел. Это чистая арифметика цикла, которую прототип может считать
и показывать до начала смены.

**5. Данные вместо ручного ввода.** Сегодня события заводятся руками и импортом CSV —
ровно так, как их и собирают на предприятии (суточный отчёт мастера смены). Дальше —
телеметрия: моточасы с бортовых систем, GPS самосвалов, весовая на приёмном бункере,
данные с частотных преобразователей. Формат события в модели под это уже подходит.

**6. Роли и площадки.** Мастер смены, начальник участка, технолог, диспетчер видят разное;
предприятий и участков у одного владельца обычно несколько. Модель `User` с ролями и поле
`site` у техники — это заготовки под многоплощадочность и разграничение прав.

**7. Связь на карьере плохая.** Реальный ввод данных идёт там, где интернета может не быть:
оффлайн-режим с последующей синхронизацией — обязательное условие внедрения, а не украшение.

Чего для этого не хватает: доступа к реальным данным одного предприятия и пилота на одном
участке. Всё перечисленное опирается на практику, а не на предположения о рынке.

- бизнес-логика решения, инструменты агента под задачу кейса

## Работа с Codex

В корне лежит [AGENTS.md](AGENTS.md) — Codex подхватывает его автоматически. Там стек,
команды, стиль и жёсткое правило: **`npm run dev` и `uvicorn` нельзя запускать как
команду проверки** — они не завершаются и вешают агента до таймаута. Проверка — `make check`.

Если правишь код руками, а не агентом, AGENTS.md всё равно полезен: это короткая памятка
по проекту.

## Если что-то не работает

| Симптом                                   | Что делать                                                      |
| ----------------------------------------- | --------------------------------------------------------------- |
| В сайдбаре «backend недоступен»           | Не поднят backend. `make dev`, проверь http://localhost:8000/docs |
| «⚠ AI в режиме заглушки»                  | Нет `OPENAI_API_KEY` в `.env`. Вставь ключ и перезапусти backend  |
| Дашборд пустой                            | Не залиты данные: `make seed`                                    |
| Поменял модель, а API отдаёт старое       | uvicorn без `--reload` держит старый код. `make dev` запускает с ним |
| `make: command not found`                 | Используй `.\make.cmd <команда>`                                 |
| 404 на модель / ошибка от OpenAI          | Поменяй `OPENAI_MODEL` в `.env` на доступную модель              |
| Кракозябры в консоли Windows              | Команды из Makefile уже ставят `PYTHONUTF8=1`; вручную — тоже    |
| Порт 8000 занят                           | `make dev BACKEND_PORT=8010` и поправь `VITE_API_URL` в `.env`   |
| На деплое пустой дашборд                  | Не выставлен `SEED_ON_START=true` — без него пустая база не наливается |
| Ссылка на Render отвечает ~40 секунд      | Бесплатный план засыпает после 15 минут простоя. Открой её заранее |
| На деплое `/fleet` отдаёт 404             | Фронт не собрался: смотри лог сборки образа, шаг `npm run build` |
