## 1. Контекст

Каркас для хакатона HackAlem AI, трек **«Добывающая промышленность»**. Предметка:
парк техники на разрезе (`Asset`) и события с ней (`Event`) — отказы, простои, ТО, аварии.
Конкретный кейс внутри трека объявляют на площадке, поэтому модели широкие и рассчитаны
на правку.

Важно про сроки: 23.09 — офлайн-этап, **24–28.09 жюри и технические эксперты проверяют
присланные проекты офлайн**, 29.09 — Demo Day. Репозиторий читают без нас, поэтому он
обязан подниматься с первого раза.

Главный приоритет — **скорость и работоспособность демо**, а не архитектурная чистота.
Правильное решение здесь то, которое понятно человеку под давлением времени.

## 2. Стек

| Слой     | Что                                                            |
| -------- | -------------------------------------------------------------- |
| Backend  | Python 3.11+, FastAPI, SQLAlchemy 2.0 (синхронный), SQLite      |
| AI       | OpenAI Python SDK, Chat Completions, Structured Outputs, tools  |
| Frontend | Vite + React 19 + TypeScript, react-router-dom, recharts        |
| Прочее   | pytest, venv в `backend/.venv`, зависимости фронта в `frontend/`|

SQLAlchemy с async-роутом можно, но это лишний источник ошибок под таймер.

## 3. Команды

```
make setup   # поставить зависимости (один раз)
make seed    # пересоздать SQLite и залить 400 демо-записей
make dev     # backend :8000 + frontend :5173
make check   # тесты бэкенда + tsc --noEmit  <- ЭТО и есть проверка
```

Windows без make: `.\make.cmd setup`, `.\make.cmd check` и т.д. — те же действия.

Напрямую, без make:

```
cd backend  && .venv/Scripts/python.exe -m pytest         # Windows
cd backend  && .venv/bin/python -m pytest                 # macOS/Linux
cd frontend && npm run typecheck
```

## 4. ⛔ Запрет: серверы не являются проверкой

**`npm run dev` и `uvicorn` НИКОГДА не запускаются как команда проверки.**
Это вечные процессы: они не завершаются, и агент, ожидающий их кода возврата, вешает сессию
до таймаута. На хакатоне это минус 10 минут из пяти часов.

- Проверять правки — только `make check` (или `pytest` / `npm run typecheck` напрямую).
- Убедиться, что фронт собирается — `npm run build`, он завершается сам.
- Реально нужно поднять сервер (например, дёрнуть эндпоинт) — **только в фоне,
  с таймаутом и обязательной остановкой после проверки**:

  ```bash
  # правильно: фон + таймаут + kill
  (cd backend && .venv/bin/python -m uvicorn app.main:app --port 8000 &) && sleep 3 \
    && curl -s --max-time 5 http://localhost:8000/api/health \
    ; pkill -f "uvicorn app.main:app"
  ```

- Любой `curl` — с `--max-time`. Любой запуск чего-то долгого — с явным таймаутом.
- Проверять эндпоинты лучше вообще без сервера, через `TestClient` в тестах (см. `backend/tests/`).

## 5. Стиль кода

- KISS и DRY. Дублирование в двух местах — норма; вводить абстракцию с третьего.
- **Не плоди слои.** Нет репозиториев, сервисов, DI-контейнеров, фабрик. Роут ходит в сессию
  напрямую — так и надо. Логика модели живёт в `backend/app/ai/`, и только там.
- Комментарии — по-русски, объясняют **почему**, а не пересказывают код. Строк на 5-10 кода —
  максимум одна строка комментария.
- Python: type hints обязательны в сигнатурах, `snake_case`, строки в двойных кавычках,
  длина строки до 120.
- TypeScript: `strict` включён, `any` не использовать, типы ответов бэкенда держать
  в `frontend/src/api.ts` рядом с функцией запроса.
- Ошибки обрабатывать явно: пустых `except:` / `catch {}` быть не должно, причину логировать
  или показывать пользователю.
- Новый файл заводить только если он реально нужен. Лучше 200 строк в существующем модуле,
  чем пять файлов по 40.

## 6. Что нельзя ломать

Это каркас демо, три вещи должны продолжать работать после любой правки:

1. **Фолбэк AI.** `backend/app/ai/client.py` не должен бросать исключения наружу. Нет ключа,
   таймаут, 500 от OpenAI — возвращается `LlmResult(status="fallback")` с заглушкой.
   Демо на сцене не имеет права упасть из-за сети.
2. **Логирование в `ai_calls`.** Каждый вызов модели пишется через `log_call()`: промпт,
   ответ, токены, латентность, стоимость. Новый вызов модели — новый лог, без исключений.
3. **`make check` зелёный.** Сломал тест — почини тест или код, но не удаляй проверку.
4. **Сценарий «залил CSV -> оценил риск отказа -> выгрузил»** — он же демо. Тесты на него
   лежат в `backend/tests/test_data_flow.py`.

## 7. Секреты

- Ключи только из `.env` через `app.config.settings`. `os.environ` напрямую и тем более
  строковые литералы с ключами — запрещены.
- `.env` в `.gitignore`. Никогда не коммить его и не печатать значение ключа в логах,
  в ответах API или в сообщениях коммита.
- Новая переменная окружения → добавить её и в `.env.example`, и в класс `Settings`.

## 9. Порядок работы над задачей

1. Прочитать файлы, которые собираешься менять, целиком — они короткие.
2. Сделать минимальное изменение, решающее ровно поставленную задачу.
   Попутный рефакторинг не начинать.
3. Прогнать `make check`.
4. Если добавил поведение — добавить один короткий тест в `backend/tests/test_smoke.py`.
5. В ответе человеку: что изменил, какие файлы, что проверил. Без пересказа кода.

Если задача противоречит этому файлу — сказать об этом прямо и предложить вариант,
а не молча сделать по-своему.
